\section*{\hspace*{\gostindent}СПИСОК СОКРАЩЕНИЙ И ТЕРМИНОВ}
% ============================================================

\begin{itemize}[leftmargin=0pt, itemindent=1.25cm, labelsep=0pt, label={}]
\item \textbf{CMS} -- Content Management System -- система управления содержимым сайта.
\item \textbf{API} -- Application Programming Interface -- программный интерфейс
  взаимодействия компонентов системы.
\item \textbf{REST} -- Representational State Transfer -- архитектурный стиль
  построения API поверх HTTP.
\item \textbf{SPA} -- Single Page Application -- одностраничное веб-приложение
  (фронтенд).
\item \textbf{DTO} -- Data Transfer Object -- объект переноса данных на границе API,
  отделённый от внутреннего представления в БД.
\item \textbf{ORM} -- Object-Relational Mapping -- отображение объектов языка
  программирования на строки реляционной таблицы.
\item \textbf{JWT} -- JSON Web Token -- формат токена авторизации, используемый для
  access-токена сессии.
\item \textbf{TLS} -- Transport Layer Security -- протокол шифрования канала связи
  (HTTPS).
\item \textbf{CI} -- Continuous Integration -- непрерывная автоматическая проверка
  (тесты, линтеры) при каждом изменении кода.
\item \textbf{СУБД} -- система управления базами данных (в проекте -- PostgreSQL 16).
\item \textbf{БД} -- база данных.
\item \textbf{ФТ} -- функциональное требование (карточки ФТ-001--ФТ-015 в техническом
  задании).
\item \textbf{Точка сети} -- отдельная парикмахерская/барбершоп в составе сети одного
  владельца -- собственный адрес, часы работы, мастера и записи.
\item \textbf{Мастер} -- сотрудник точки, оказывающий услуги клиентам; в системе --
  роль пользователя.
\end{itemize}

\section*{\hspace*{\gostindent}ВВЕДЕНИЕ}
\addcontentsline{toc}{section}{ВВЕДЕНИЕ}
% ============================================================

Предприятия сферы парикмахерских услуг и барберинга всё чаще переходят
от бумажных журналов и разрозненных таблиц к специализированным
программным системам. Такие решения обеспечивают онлайн-запись
клиентов, ведение расписания мастеров и автоматизацию отчётности.
Отсутствие единого инструмента порождает типовые для отрасли проблемы:
возникновение накладок в расписании (двойных записей), неявки клиентов
из-за отсутствия напоминаний, сложности с дифференцированным учётом цен
мастеров, а также отсутствие у руководства оперативной аналитики по
выручке и загрузке заведений. Настоящий документ посвящён
веб-приложению «Сайтама», автоматизирующему данные бизнес-процессы для
отдельных салонов и сетевых барбершопов.

В работе формулируется решаемая задача, описываются автоматизируемые
процессы, архитектура приложения, применённые паттерны проектирования и
требования нормативно-правовой базы. Обосновывается выбор
технологического стека (FastAPI [7], SQLAlchemy [8], PostgreSQL [12]),
приводится схема базы данных, детально рассматривается логика ключевых
пользовательских сценариев, интеграция аналитических модулей и
развёртывание сервиса в сети Интернет.

Комплект проектной документации включает три сопутствующих документа:

\begin{enumerate}
\item Техническое задание, оформленное в соответствии с
  ГОСТ 34.602-2020 [1] и ГОСТ 19.201-78 [2], содержащее постановку
  задачи и перечень функциональных требований (ФТ-001--ФТ-015);
\item Руководство пользователя, описывающее пошаговые сценарии работы
  для четырёх ролей: клиента, мастера, администратора филиала и
  владельца сети;
\item Руководство администратора, регламентирующее процедуры
  развёртывания, эксплуатации и резервного копирования серверной
  инфраструктуры.
\end{enumerate}

Практическая значимость результатов заключается в создании готовой к
промышленному внедрению программной платформы, устраняющей издержки
ручного учёта и человеческого фактора. Архитектура системы изначально
поддерживает мультифилиальность, что позволяет развёртывать её как в
единичных парикмахерских, так и в разветвлённых сетях без внесения
изменений в исходный код.

Структура работы включает введение, аналитическую часть, проектную
часть, заключение, библиографический список и приложения.

% ============================================================
\gostsection{1}{ПОСТАНОВКА ЗАДАЧИ}
% ============================================================

\textbf{Исходная проблема.} Барбершоп «Сайтама», выбранный пилотным
объектом внедрения, вёл запись клиентов и учёт услуг вручную (телефон,
бумажный журнал, разрозненные записи) -- это порождало типовые для отрасли
проблемы: двойные записи одного мастера на одно и то же время, отсутствие
напоминаний клиентам и, как следствие, неявки (no-show), отсутствие
единого каталога услуг с ценами, различающимися по мастеру, и отсутствие
у владельца оперативной картины по выручке и загруженности без ручного
подсчёта.

\textbf{Задача.} Разработать веб-приложение, автоматизирующее полный цикл
операционной деятельности барбершопа: онлайн-запись клиента без участия
администратора, ведение каталога услуг с индивидуальным прайсом по
мастерам, автоматические напоминания о визите, формирование отчётов по
выручке и загруженности, и -- что не было предусмотрено первоначальной
редакцией технического задания, но было добавлено по ходу разработки --
поддержку сети из нескольких точек с ролью владельца сети поверх
администратора отдельной точки.

\textbf{Измеримые цели} (полный перечень с формулировками показателей --
техническое задание, раздел 2.2): сокращение времени оформления записи
клиентом до 2 минут; исключение двойных бронирований техническими
средствами (ограничением целостности СУБД, а не организационно);
снижение доли неявок за счёт автоматических напоминаний; поддержка
индивидуального прайса услуги по мастеру; отказ от бумажных/табличных
журналов в пользу единого хранилища данных; формирование отчёта по
выручке и загруженности без участия разработчика.

\textbf{Границы задачи.} Вне рамок разработки остались: приём онлайн-оплаты
(оплата очно, см. техническое задание, раздел 3.2), бухгалтерский и
складской учёт, CRM-функции сверх базового профиля клиента (сегментация,
маркетинговые рассылки, программы лояльности). Эти ограничения не
изменились по ходу разработки.

\gostsection{2}{АВТОМАТИЗИРУЕМЫЕ БИЗНЕС-ПРОЦЕССЫ}
% ============================================================

Система автоматизирует следующие бизнес-процессы, выделенные при
обследовании предметной области (техническое задание, раздел 2.1):

\begin{enumerate}
  \item онлайн-запись клиента (Зап-1) -- выбор услуги, мастера,
        свободного времени и подтверждение записи без участия
        администратора; для незарегистрированного клиента запись создаёт
        учётную запись автоматически (см. раздел 8);
  \item управление услугами и прайсом (Усл-2) -- единый каталог услуг с
        ценой, индивидуальной по каждой паре «мастер -- услуга»;
  \item напоминания о записи (Увед-3) -- автоматическая отправка
        напоминаний за 24 и за 2 часа до визита;
  \item формирование отчётов (Отчёт-4) -- выручка, загруженность
        мастеров, топ-услуги за произвольный период, без привлечения
        разработчика (раздел 9);
  \item управление контентом сайта (Конт-5) -- настройки, отображаемые на
        главной странице и странице мастеров;
  \item управление сетью точек обслуживания (Точ-6) -- открытие, закрытие,
        изменение адреса, телефона и часов работы каждой точки.
\end{enumerate}

\textbf{Процесс, добавленный по ходу разработки.} Управление сетью точек
обслуживания (Точ-6) не входило в первую редакцию технического задания --
поддержка сети из нескольких точек (роль «владелец сети» шире
«администратора точки», переключение между точками, назначение
администратора конкретной точке) была добавлена по ходу разработки, и
техническое задание обновлено вместе с кодом. Функции по ролям
(клиент/мастер/администратор/владелец) с полным перечнем операций --
руководство пользователя, разделы 3.4.1--3.4.4.

приложение (SPA) на Vue 3 [11], обращающееся к REST API на FastAPI [7],

\gostsubsection{3.2}{Архитектурные шаблоны бэкенда}

Backend (\envvar{backend/app/}) построен как строгая однонаправленная
слоистая архитектура -- \texttt{routes} $\to$ \texttt{services} $\to$
\texttt{repositories} $\to$ \texttt{models}, -- с параллельным пакетом
\texttt{schemas/} Pydantic-схем [10], используемых только на границе запроса:
сервисы всегда возвращают \envvar{XResponse.model\_validate(orm\_obj)},
поэтому «сырые» ORM-объекты никогда не попадают наружу через HTTP. Внутри
этой схемы использовано несколько именованных шаблонов проектирования:

\begin{itemize}
  \item \textbf{DTO на границе (Data Transfer Object).} Разделение
        \texttt{schemas/} (что видит клиент API) и \texttt{models/} (как
        данные лежат в БД) -- изменение внутреннего представления не ломает
        контракт API, и наоборот.
  \item \textbf{Repository.} Один класс-репозиторий на агрегат (\texttt{UserRepository},
        \texttt{AppointmentRepository}, \texttt{SalonRepository} и т.\,д.) --
        вся работа с SQLAlchemy [8] сосредоточена в этом слое; сервисы не
        составляют SQL-запросы напрямую.
  \item \textbf{Dependency Injection через \texttt{Depends}.} Отдельного
        DI-контейнера нет -- вся инъекция зависимостей идёт штатным
        механизмом FastAPI. \texttt{get\_db()} -- сессия БД на один
        запрос, реализующая шаблон \textbf{Unit of Work}: один
        \texttt{commit} при успешном завершении запроса, \texttt{rollback}
        при любом исключении, \texttt{db.close()} в \texttt{finally}.
  \item \textbf{Dependency-factory.} \envvar{require\_role(*roles)} --
        функция, возвращающая функцию-зависимость; так собраны
        \envvar{get\_current\_client/master/admin/owner}. Поскольку
        \texttt{owner} $\supset$ \texttt{admin} по бизнес-правилу,
        \texttt{get\_current\_admin} проверяет обе роли сразу.
  \item \textbf{Явное разрешение области видимости (salon scoping).}
        Хелпер \envvar{resolve\_salon\_scope(current\_user, salon\_id)}
        -- не \texttt{Depends}, а обычная функция, вызываемая внутри уже
        защищённых ролью эндпоинтов: для \texttt{owner} отсутствие
        \texttt{salon\_id} означает «вся сеть», для \texttt{admin} --
        доступ жёстко ограничен собственной точкой (несовпадение --
        код ответа 403).
\end{itemize}

\gostsubsection{3.3}{Архитектура фронтенда}

Frontend (\envvar{frontend/src/}) -- Vue 3 на Composition API
(\texttt{<script setup>} повсеместно, без TypeScript), Vue Router 4,
управление состоянием -- Pinia (шесть «setup-хранилищ» --
\texttt{auth}, \texttt{salon}, \texttt{setup}, \texttt{siteContent},
\texttt{masterProfile}, \texttt{toast}). Маршрутизация -- один файл
\envvar{router/index.js} с ленивой загрузкой всех маршрутов и единым
глобальным \texttt{beforeEach}-хуком, который, помимо проверки ролей
(\texttt{meta.roles}), принудительно блокирует всё приложение мастером
первого запуска \texttt{/setup}, пока тот не завершён (см. раздел 8.2).

Два решения на уровне фронтенда стоит выделить отдельно как архитектурные,
не просто UI-детали:

\begin{itemize}
  \item \textbf{Токен сессии -- только в httpOnly cookie}, никогда не в
        \envvar{localStorage}/JS-переменной (снижает риск кражи токена через XSS).
        Обновление токена -- через axios-интерцептор с \emph{single-flight}:
        при 401 запускается один \envvar{POST /auth/refresh},
        параллельные запросы дожидаются общего promise вместо каждый --
        своего обновления, и только при неудаче самого refresh срабатывает
        глобальный logout.
  \item \textbf{Тема оформления как настройка, а не константа.} Цвета
        бренда (\envvar{brand/accent/ink/stone})
        объявлены в Tailwind не фиксированными значениями, а CSS custom
        properties, переключаемыми во время выполнения из настроек сайта,
        заданных администратором -- один и тот же собранный фронтенд
        обслуживает точки с разным оформлением без пересборки.
\end{itemize}

\gostsection{4}{ТРЕБОВАНИЯ ЗАКОНОДАТЕЛЬСТВА}
% ============================================================

Согласно техническому заданию (раздел 1.4), система должна соответствовать
Федеральному закону № 152-ФЗ «О персональных данных» [5] и Федеральному
закону № 149-ФЗ «Об информации, информационных технологиях и о защите
информации» [6]; методология оценки достаточности реализованных мер
защиты опирается на критерии ГОСТ Р ИСО/МЭК 15408-3-2008 [4]. Ниже --
то, что из них фактически реализовано в коде.

\begin{itemize}
  \item \textbf{Согласие на обработку персональных данных.} Форма
        регистрации требует явной отметки согласия (чекбокс со ссылкой на
        политику конфиденциальности) -- отправка формы блокируется, пока
        согласие не отмечено; то же условие распространено на вход через
        VK ID.
  \item \textbf{Страница политики конфиденциальности} (маршрут
        \texttt{/privacy}) -- десять разделов, соответствующих типовой
        структуре документа по 152-ФЗ (правовые основания, категории
        данных, цели обработки, права пользователя, раскрытие
        использования cookie и аналитики, контактные данные оператора).
  \item \textbf{Раскрытие использования cookie и аналитики} в §8 политики
        конфиденциальности вместе с фактом использования Яндекс.Метрики
        (раздел 9).
  \item \textbf{Хранение и удаление персональных данных.} Пароли не
        хранятся в открытом виде (хэш пароля, поле \texttt{password\_hash});
        удаление учётной записи при наличии связанных записей о визитах
        технически заблокировано ограничением ссылочной целостности
        (\texttt{ON DELETE RESTRICT}) -- вместо удаления применяется мягкая
        блокировка (\texttt{is\_blocked}).
\end{itemize}

\gostsubsection{7.2}{Даталогическая модель}

Фактическая схема БД насчитывает 13 таблиц (15 миграций Alembic [9] в
директории \envvar{backend/alembic/versions/}):

\begin{itemize}
  \item \texttt{salons} -- точки сети (адрес, часы работы, slug);
  \item \texttt{users} -- учётные записи всех ролей (client/master/admin/owner);
  \item \texttt{masters} -- профиль мастера (специализация, коэффициент к цене);
  \item \texttt{schedules} -- рабочее расписание мастера по дням недели;
  \item \texttt{services} -- каталог услуг (цена, длительность);
  \item \texttt{master\_services} -- прайс услуги, индивидуальный по мастеру;
  \item \texttt{appointments} -- записи на приём (\texttt{EXCLUDE USING gist}
        -- защита от двойного бронирования на уровне СУБД);
  \item \texttt{reviews} -- отзывы клиентов о завершённых записях;
  \item \texttt{sessions} -- серверное хранилище refresh-сессий;
  \item \envvar{password\_reset\_tokens}, \envvar{email\_verification\_tokens} --
        одноразовые токены сброса пароля и подтверждения email;
  \item \texttt{login\_attempts} -- аудит попыток входа;
  \item \texttt{site\_settings} -- редактируемый контент сайта (единственная
        строка, JSONB).
\end{itemize}

% ============================================================
\gostsection{9}{ПОДКЛЮЧЕНИЕ АНАЛИТИКИ}
% ============================================================

В системе три независимых источника аналитики, которые не стоит путать
между собой:

\begin{itemize}
  \item \textbf{Веб-аналитика (Яндекс.Метрика) -- подключена и активна.}
        Счётчик загружается отдельным статическим файлом
        (\texttt{/metrika.js}), а не инлайн-скриптом в
        \texttt{index.html}, -- ради политики безопасности контента (CSP):
        \envvar{script-src} остаётся \texttt{'self'} без исключения
        \envvar{'unsafe-inline'}. Использование раскрыто в §8 политики
        конфиденциальности (раздел 4).
  \item \textbf{Мониторинг ошибок (Sentry) -- код готов, отключён по
        умолчанию.} Инициализация присутствует и на бэкенде, и на
        фронтенде, но выполняется только при заданном
        \texttt{SENTRY\_DSN}/\texttt{VITE\_SENTRY\_DSN}.
  \item \textbf{Бизнес-аналитика -- собственные отчёты по данным
        приложения.} Раздел «Статистика» (KPI-плитки, график регистраций
        за 30 дней) и раздел «Отчёты» (выручка и загруженность по
        дням/мастерам/услугам с экспортом в Excel) -- оба на данных из
        собственной БД проекта, без внешнего сервиса. Реализуют цель
        технического задания «формирование отчёта по выручке и
        загруженности без привлечения разработчика» (раздел 2.2); полное
        описание экранов -- руководство пользователя, раздел 3.4.3.
\end{itemize}

\section*{\hspace*{\gostindent}ЗАКЛЮЧЕНИЕ}
\addcontentsline{toc}{section}{ЗАКЛЮЧЕНИЕ}
% ============================================================

В ходе разработки создана и доведена до готовности к развёртыванию CMS
«Сайтама» -- веб-приложение для автоматизации онлайн-записи и
операционной деятельности сети барбершопов.

\textbf{Соответствие целям технического задания.} Ключевые измеримые цели
(раздел 2.2 технического задания) обеспечены технически: двойное
бронирование исключено ограничением целостности СУБД, а не
организационно (раздел 8); индивидуальный прайс по мастеру, единое
хранилище данных и отчёт по выручке/загруженности без участия
разработчика -- реализованы и доступны в интерфейсе администратора
(раздел 9). Часть целей (снижение доли неявок за счёт напоминаний, доля
клиентов, выбирающих вход через VK ID) сформулирована как показатель,
измеримый только на реальной эксплуатации.

\textbf{Не входило в объём технического задания.} Второй OAuth-провайдер и
другие каналы уведомлений (Telegram, SMS) техническим заданием не
предусматривались -- вход реализован только по email/паролю и через VK ID
(раздел 3), рассылка -- только по email (раздел 2). Отдельная таблица
журнала аудита критичных операций также не реализована -- частично её
роль выполняет таблица попыток входа \texttt{login\_attempts} (раздел 7).

\textbf{Направления дальнейшего развития.} Второй OAuth-провайдер и
дополнительные каналы уведомлений можно добавить без изменения
архитектуры (раздел 3 уже отделяет бизнес-логику сервисов от конкретного
канала доставки/провайдера); горизонтальное масштабирование backend
потребует пересмотра внутрипроцессных механизмов защиты от перебора
паролей и ограничения частоты запросов (раздел 5) в пользу общего
хранилища состояния; полноценный журнал аудита -- отдельная таблица с
записью каждой критичной операции, а не только попыток входа.

Итоговое состояние проекта, полный перечень функциональных требований и
инструкции по эксплуатации -- см. соответственно техническое задание,
руководство пользователя и руководство администратора.
