# Стандарт именования объектов баз данных

---

## 1. Цель и область применения

Настоящий документ устанавливает единые правила именования таблиц, полей, индексов и ограничений для всех реляционных баз данных в проекте.

* **Обязательность:** стандарт обязателен к применению при проектировании новых схем данных и рефакторинге существующих.
* **Ключевые критерии:** читаемость, однозначность и высокая переносимость между различными СУБД (*PostgreSQL*, *MySQL*, *Oracle*, *MS SQL Server* и др.).

---

## 2. Общие принципы

| Параметр | Правило | Описание | Исключения и пояснения |
| :--- | :--- | :--- | :--- |
| **Регистр символов** | `snake_case` | Только нижний регистр символов. | В разных СУБД регистрозависимость идентификаторов различается; единый нижний регистр нивелирует ошибки при миграции. |
| **Допустимые символы** | `[a-z0-9_]` | Только строчные латинские буквы, цифры и символ подчёркивания. | Дефисы, пробелы, кириллица и спецсимволы **запрещены** — они требуют экранирования и нарушают переносимость. |
| **Максимальная длина** | $\le$ 60 символов | Гарантированно поддерживается всеми популярными СУБД (например, PostgreSQL ограничивает длину 63 байтами). | Рекомендуется удерживать длину идентификаторов в пределах **50 символов** для лучшей читаемости. |
| **Зарезервированные слова** | Запрещены | Запрещено использовать ключевые слова SQL (например, `user`, `order`, `table`, `group`, `check`). | При необходимости следует добавлять уточняющий суффикс (`user_account`, `order_header`) или применять синонимы. |

## 3. Именование таблиц

### 3.1. Базовые правила
* **Единственное число:** имя таблицы задаётся в единственном числе и отражает тип сущности (например, `product`, `customer`, `order_item`).
* **Разделитель:** составные имена разделяются символом подчёркивания (`order_item`, `user_session`).
* **Префиксы модулей:** используются только для логической группировки в крупных монолитных системах (например, `cms_page`, `payment_transaction`). В микросервисной архитектуре рекомендуется логическое разделение по отдельным схемам или базам данных (см. [раздел 8.2](#82-схемы-и-базы-данных)).

### 3.2. Специальные типы таблиц

| Тип таблицы | Соглашение по именованию | Примеры |
| :--- | :--- | :--- |
| **Связующая** *(many-to-many)* | Имена двух связываемых сущностей в алфавитном порядке через `_` | `product_category`, `user_role` |
| **Историческая / Логи** | Имя сущности + суффикс `_history` или `_log` (в зависимости от бизнес-логики) | `order_history`, `price_change_log` |
| **Временная / Стадирующая** | Префикс `tmp_` или `staging_` | `tmp_import_data`, `staging_orders` |
| **Справочная** *(словарь)* | Существительное в единственном числе | `country`, `currency`, `order_status` |

## 4. Именование полей

### 4.1. Системные поля
Обязательны для всех основных сущностей:

| Поле | Назначение | Рекомендуемый тип (общий) | Специфика СУБД |
| :--- | :--- | :--- | :--- |
| `id` | Суррогатный первичный ключ (PK) | `BIGINT` | **PostgreSQL:** `BIGSERIAL` / `BIGINT GENERATED BY DEFAULT AS IDENTITY`<br>**MySQL:** `BIGINT AUTO_INCREMENT`<br>**Oracle:** `NUMBER(19) GENERATED BY DEFAULT AS IDENTITY`<br>**MS SQL Server:** `BIGINT IDENTITY(1,1)` |

### 4.2. Поля внешних ключей (FK)
* **Стандартный шаблон:** `<имя_целевой_таблицы>_id` (в единственном числе, например, `order_id`, `status_id`).
* **Несколько связей с одной таблицей:** добавляется смысловой префикс роли:
  * `created_by` / `updated_by` / `approved_by`
  * `manager_id`, `parent_id`
* **Ограничение NULL:** явное указание `NOT NULL` для обязательных связей и допустимость `NULL` для опциональных отношений.

### 4.3. Рекомендации по выбору типов данных для переносимости

| Логический тип | MySQL | PostgreSQL | Oracle | MS SQL Server |
| :--- | :--- | :--- | :--- | :--- |
| **Целочисленный ID** | `BIGINT AUTO_INCREMENT` | `BIGINT GENERATED ... AS IDENTITY` | `NUMBER(19) GENERATED ... AS IDENTITY` | `BIGINT IDENTITY(1,1)` |
| **Строка фикс. длины** | `CHAR(n)` | `CHAR(n)` | `CHAR(n)` | `CHAR(n)` |
| **Строка перем. длины** | `VARCHAR(n)` | `VARCHAR(n)` | `VARCHAR2(n)` | `VARCHAR(n)` / `NVARCHAR(n)` |
| **Длинный текст** | `TEXT` / `LONGTEXT` | `TEXT` | `CLOB` | `NVARCHAR(MAX)` |
| **Фиксированная точка** | `DECIMAL(p,s)` | `NUMERIC(p,s)` | `NUMBER(p,s)` | `DECIMAL(p,s)` |
| **Дата и время** | `DATETIME` / `TIMESTAMP` | `TIMESTAMP WITH TIME ZONE` | `TIMESTAMP` | `DATETIME2` |
| **Логический** | `BOOLEAN` / `TINYINT(1)` | `BOOLEAN` | `CHAR(1)` / `NUMBER(1)` | `BIT` |

## 5. Именование индексов

### 5.1. Шаблоны и префиксы

| Тип индекса | Префикс | Формат имени | Пример |
| :--- | :--- | :--- | :--- |
| **Первичный ключ** | — | Системное имя `PRIMARY` (или `pk_<таблица>` при явном задании) | `pk_order` |
| **Уникальный** | `uniq_` | `uniq_<таблица>_<поле1>_<поле2>` | `uniq_user_email`, `uniq_order_number` |
| **Обычный (B-Tree)** | `idx_` | `idx_<таблица>_<поле1>_<поле2>` *(порядок полей как в определении)* | `idx_order_user_id`, `idx_order_user_status` |
| **Полнотекстовый** | `ft_` | `ft_<таблица>_<поле>` | `ft_product_name` |
| **Пространственный** | `sp_` | `sp_<таблица>_<поле>` | `sp_geo_location` |

> **Примечание:** Префиксные индексы (ограничение длины индексируемой части строки) не рекомендуются, так как их поддержка и поведение различаются между СУБД. При необходимости оптимизации используйте хеширование или отдельное вычисляемое поле.

## 6. Именование ограничений (Constraints)

### 6.1. Внешние ключи (FOREIGN KEY)
* **Базовый формат:** `fk_<дочерняя_таблица>_<родительская_таблица>`
* **Несколько внешних ключей на одну таблицу:** `fk_<дочерняя_таблица>_<роль>_<родительская_таблица>`
  * *Пример:* `fk_order_created_by_user`
* *Синтаксический пример:*
  ```sql
  CONSTRAINT fk_order_user FOREIGN KEY (user_id) REFERENCES user(id)
  ```

### 6.2. Проверочные ограничения (CHECK)
* **Формат:** `chk_<таблица>_<краткое_описание>`
* *Синтаксический пример:*
  ```sql
  CONSTRAINT chk_product_price_positive CHECK (price > 0)
  ```

### 6.3. Ограничения уникальности (UNIQUE)
* При создании через `CONSTRAINT` именуются по шаблону `uniq_<таблица>_<поля>`.
* **Рекомендация:** для единообразного администрирования структуры индексов предпочтительнее создавать явные уникальные индексы с помощью конструкции `CREATE UNIQUE INDEX`.

## 7. Полный пример (Универсальный DDL)

Ниже приведён эталонный пример создания таблицы заказов со всеми связанными объектами:

```sql
-- Таблица заказов
-- Примечание: в реальных проектах предпочтительнее имя без кавычек (order_header / customer_order)
CREATE TABLE "order" (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id      BIGINT NOT NULL,
    status_id    BIGINT NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL,
    number       VARCHAR(50) NOT NULL,
    created_at   TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at   TIMESTAMP WITH TIME ZONE,
    created_by   BIGINT NOT NULL,
    updated_by   BIGINT,

    -- Ограничения (Constraints)
    CONSTRAINT fk_order_user       FOREIGN KEY (user_id) REFERENCES "user"(id),
    CONSTRAINT fk_order_status     FOREIGN KEY (status_id) REFERENCES order_status(id),
    CONSTRAINT fk_order_created_by FOREIGN KEY (created_by) REFERENCES "user"(id),
    CONSTRAINT fk_order_updated_by FOREIGN KEY (updated_by) REFERENCES "user"(id),
    CONSTRAINT chk_order_amount_positive CHECK (total_amount >= 0)
);

-- Индексы
CREATE UNIQUE INDEX uniq_order_number     ON "order" (number);
CREATE INDEX        idx_order_user        ON "order" (user_id);
CREATE INDEX        idx_order_status      ON "order" (status_id);
CREATE INDEX        idx_order_created_at  ON "order" (created_at);
CREATE INDEX        idx_order_user_status ON "order" (user_id, status_id);
```

### Адаптация под конкретные СУБД:
* **PostgreSQL:** оставить как есть; для поля `updated_at` рекомендуется настроить триггерную функцию автообновления времени изменения.
* **MySQL:** заменить `GENERATED BY DEFAULT AS IDENTITY` на `AUTO_INCREMENT`, а `TIMESTAMP WITH TIME ZONE` — на `DATETIME` или `TIMESTAMP`.
* **Oracle:** использовать тип `NUMBER(19)` вместо `BIGINT`, `VARCHAR2` вместо `VARCHAR`.
* **MS SQL Server:** заменить `GENERATED ... AS IDENTITY` на `IDENTITY(1,1)`, для временных меток использовать `DATETIME2`.

## 8. Дополнительные рекомендации

### 8.1. Комментарии
* Для каждой таблицы и каждого атрибута обязательно добавлять комментарий (`COMMENT` в MySQL / PostgreSQL, `COMMENT ON` в Oracle).
* Комментарий должен явно раскрывать:
  * бизнес-смысл сущности или поля;
  * единицы измерения (например, граммы, копейки, миллисекунды);
  * перечень допустимых значений для статусов и кодов.

### 8.2. Схемы и базы данных
* **PostgreSQL / MS SQL Server:** группируйте таблицы по смысловым модулям с помощью изолированных схем (`cms.page`, `payment.transaction`). Это исключает потребность в длинных префиксах в именах таблиц.
* **MySQL:** понятие схемы синонимично базе данных. При масштабировании модули разносятся по отдельным логическим БД.

### 8.3. Согласованность и контроль
* Единый стиль обязателен для всех участников команды разработки и аналитики данных.
* Нарушения конвенции не допускаются и должны контролироваться на этапе Code Review и линтерами миграций.

---

## 9. Заключение

Соблюдение данного стандарта гарантирует единообразие кодовой базы, упрощает онбординг инженеров и снижает стоимость поддержки и масштабирования систем.

> **Важно:** любые отступления в исключительных случаях (специфические GIN/GiST-индексы, геоданные, партиционирование) допускаются исключительно с фиксацией обоснования в архитектурной документации (ADR).
