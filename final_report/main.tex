\textbf{Область применения документа.} Документ подводит итог разработки
CMS «Сайтама»: формулирует решаемую задачу, описывает автоматизируемые
бизнес-процессы, архитектуру и применённые архитектурные шаблоны,
требования законодательства и их реализацию, обоснование выбора
технологического стека, состав вспомогательных инструментов разработки,
структуру базы данных, работу ключевых сценариев приложения, интеграцию
аналитики и способ размещения системы в сети Интернет.

\textbf{Перечень документации, с которой связан отчёт.} Три документа
проекта детализируют то, что в настоящем отчёте описано на уровне обзора:
техническое задание -- первоначальную постановку задачи и полный перечень
функциональных требований (карточки ФТ-001--ФТ-015); руководство
пользователя -- пошаговые инструкции по работе с системой для всех четырёх
ролей (клиент, мастер, администратор точки, владелец сети); руководство
администратора -- развёртывание, эксплуатацию и резервное копирование
серверной части. Настоящий отчёт этот материал не дублирует, а ссылается
на него там, где нужны подробности.

\textbf{Уровень подготовки читателя.} Документ рассчитан на читателя с
базовым представлением о веб-разработке: клиент-серверная архитектура,
REST API, реляционные базы данных и SQL, основы контейнеризации (Docker).
Специальных знаний Python/FastAPI или Vue.js для понимания отчёта не
требуется -- технологические решения объясняются по мере изложения.

\section{ПОСТАНОВКА ЗАДАЧИ}
% ============================================================

\textbf{Исходная проблема.} Барбершоп «Сайтама», выбранный пилотным
объектом внедрения, вёл запись клиентов и учёт услуг вручную (телефон,
бумажный журнал, разрозненные записи) -- это порождало типовые для отрасли
проблемы: двойные записи одного мастера на одно и то же время, отсутствие
напоминаний клиентам и, как следствие, неявки (no-show), отсутствие
единого каталога услуг с ценами, различающимися по мастеру, и отсутствие
у владельца оперативной картины по выручке и загруженности без ручного
подсчёта.

\textbf{Задача.} Разработать веб-приложение, автоматизирующее полный цикл
операционной деятельности барбершопа: онлайн-запись клиента без участия
администратора, ведение каталога услуг с индивидуальным прайсом по
мастерам, автоматические напоминания о визите, формирование отчётов по
выручке и загруженности, и -- что не было предусмотрено первоначальной
редакцией технического задания, но было добавлено по ходу практики --
поддержку сети из нескольких точек с ролью владельца сети поверх
администратора отдельной точки.

\textbf{Измеримые цели} (полный перечень с формулировками показателей --
техническое задание, раздел 2.2): сокращение времени оформления записи
клиентом до 2 минут; исключение двойных бронирований техническими
средствами (ограничением целостности СУБД, а не организационно);
снижение доли неявок за счёт автоматических напоминаний; поддержка
индивидуального прайса услуги по мастеру; отказ от бумажных/табличных
журналов в пользу единого хранилища данных; формирование отчёта по
выручке и загруженности без участия разработчика.

\textbf{Границы задачи.} Вне рамок разработки остались: приём онлайн-оплаты
(оплата очно, см. техническое задание, раздел 3.2), бухгалтерский и
складской учёт, CRM-функции сверх базового профиля клиента (сегментация,
маркетинговые рассылки, программы лояльности). Эти ограничения не
изменились по ходу практики.

\section{АВТОМАТИЗИРУЕМЫЕ БИЗНЕС-ПРОЦЕССЫ}
% ============================================================

Система автоматизирует пять бизнес-процессов, выделенных при
обследовании предметной области (техническое задание, раздел 2.1):

\begin{itemize}
  \item \textbf{Онлайн-запись клиента} (Зап-1) -- выбор услуги, мастера,
        свободного времени и подтверждение записи без участия
        администратора; для незарегистрированного клиента запись создаёт
        учётную запись автоматически (см. раздел 8).
  \item \textbf{Управление услугами и прайсом} (Усл-2) -- единый каталог
        услуг с ценой, индивидуальной по каждой паре «мастер -- услуга».
  \item \textbf{Уведомления и напоминания} (Увед-3) -- автоматическая
        отправка напоминаний за 24 и за 2 часа до визита.
  \item \textbf{Формирование отчётов} (Отчёт-4) -- выручка, загруженность
        мастеров, топ-услуги за произвольный период, без привлечения
        разработчика (раздел 9.3).
  \item \textbf{Управление контентом сайта} -- редактирование главной
        страницы, страницы мастеров и настроек точки без правки кода.
\end{itemize}

\textbf{Расхождение с первоначальным планом: канал уведомлений.}
Техническое задание закладывало многоканальную доставку уведомлений
(email, SMS, Telegram Bot API) с выбором канала по приоритету получателя.
По факту реализован только канал email (SMTP) -- Telegram Bot API и
SMS-провайдер не подключались; в первой миграции схемы БД была
предусмотрена таблица для многоканального журнала уведомлений, но она не
была задействована ни одним сервисом и впоследствии удалена как мёртвая
схема (раздел 7). Причина сужения -- типовой для практики компромисс
«время на практику ограничено, email закрывает и подтверждение регистрации,
и восстановление пароля, и напоминания одним и тем же уже написанным
механизмом отправки»: расширение до Telegram/SMS осталось в объёме
задокументированных, но не реализованных возможностей (см. заключение).

\textbf{Процесс, добавленный сверх первоначального плана.} По ходу
практики к пилотному барбершопу «Сайтама» добавилась поддержка сети из
нескольких точек: роль «владелец сети» (шире «администратора точки»),
переключение между точками, назначение администратора конкретной точке.
Функции по ролям (клиент/мастер/администратор/владелец) с полным перечнем
операций -- руководство пользователя, разделы 3.4.1--3.4.4.

\subsection{Архитектурные шаблоны бэкенда}

Backend (\envvar{backend/app/}) построен как строгая однонаправленная
слоистая архитектура -- \texttt{routes} $\to$ \texttt{services} $\to$
\texttt{repositories} $\to$ \texttt{models}, -- с параллельным пакетом
\texttt{schemas/} Pydantic-схем, используемых только на границе запроса:
сервисы всегда возвращают \envvar{XResponse.model\_validate(orm\_obj)},
поэтому «сырые» ORM-объекты никогда не попадают наружу через HTTP. Внутри
этой схемы использовано несколько именованных шаблонов проектирования:

\begin{itemize}
  \item \textbf{DTO на границе (Data Transfer Object).} Разделение
        \texttt{schemas/} (что видит клиент API) и \texttt{models/} (как
        данные лежат в БД) -- изменение внутреннего представления не ломает
        контракт API, и наоборот.
  \item \textbf{Repository.} Один класс-репозиторий на агрегат (\texttt{UserRepository},
        \texttt{AppointmentRepository}, \texttt{SalonRepository} и т.\,д.) --
        вся работа с SQLAlchemy сосредоточена в этом слое; сервисы не
        составляют SQL-запросы напрямую. Общей абстрактной
        репозитория-базы или generic CRUD-класса нет осознанно -- общая
        логика (пагинация, экранирование \texttt{LIKE}) вынесена
        свободными функциями, а не наследованием, что проще для
        относительно небольшого числа репозиториев проекта.
  \item \textbf{Dependency Injection через \texttt{Depends}.} Отдельного
        DI-контейнера нет -- вся инъекция зависимостей идёт штатным
        механизмом FastAPI. \texttt{get\_db()} -- сессия БД на один
        запрос, реализующая шаблон \textbf{Unit of Work}: один
        \texttt{commit} при успешном завершении запроса, \texttt{rollback}
        при любом исключении, \texttt{db.close()} в \texttt{finally}.
  \item \textbf{Dependency-factory.} \envvar{require\_role(*roles)} --
        функция, возвращающая функцию-зависимость; так собраны
        \envvar{get\_current\_client/master/admin/owner}. Поскольку
        \texttt{owner} $\supset$ \texttt{admin} по бизнес-правилу,
        \texttt{get\_current\_admin} проверяет обе роли сразу.
  \item \textbf{Явное разрешение области видимости (salon scoping).}
        Хелпер \envvar{resolve\_salon\_scope(current\_user, salon\_id)}
        -- не \texttt{Depends}, а обычная функция, вызываемая внутри уже
        защищённых ролью эндпоинтов: для \texttt{owner} отсутствие
        \texttt{salon\_id} означает «вся сеть», для \texttt{admin} --
        доступ жёстко ограничен собственной точкой (несовпадение --
        код ответа 403).
\end{itemize}

\subsection{Архитектура фронтенда}

Frontend (\envvar{frontend/src/}) -- Vue 3 на Composition API
(\texttt{<script setup>} повсеместно, без TypeScript), Vue Router 4,
управление состоянием -- Pinia (шесть «setup-хранилищ» --
\texttt{auth}, \texttt{salon}, \texttt{setup}, \texttt{siteContent},
\texttt{masterProfile}, \texttt{toast}); Vuex в проекте не используется.
Небольшая переиспользуемая логика (состояние ошибок формы, отложенное
наблюдение) вынесена в \envvar{composables/}, а не в хранилища.
Маршрутизация -- один файл \envvar{router/index.js} с ленивой загрузкой
всех маршрутов и единым глобальным \texttt{beforeEach}-хуком, который,
помимо проверки ролей (\texttt{meta.roles}), принудительно блокирует всё
приложение мастером первого запуска \texttt{/setup}, пока тот не завершён
(см. раздел 8.2).

Два решения на уровне фронтенда стоит выделить отдельно как архитектурные,
не просто UI-детали:

\begin{itemize}
  \item \textbf{Токен сессии -- только в httpOnly cookie}, никогда не в
        \envvar{localStorage}/JS-переменной (снижает риск кражи токена через XSS).
        Обновление токена -- через axios-интерцептор с \emph{single-flight}:
        при 401 запускается один \envvar{POST /auth/refresh},
        параллельные запросы дожидаются общего promise вместо каждый --
        своего обновления, и только при неудаче самого refresh срабатывает
        глобальный logout.
  \item \textbf{Тема оформления как настройка, а не константа.} Цвета
        бренда (\envvar{brand/accent/ink/stone})
        объявлены в Tailwind не фиксированными значениями, а CSS custom
        properties, переключаемыми во время выполнения из настроек сайта,
        заданных администратором -- один и тот же собранный фронтенд
        обслуживает точки с разным оформлением без пересборки.
\end{itemize}

\section{ТРЕБОВАНИЯ ЗАКОНОДАТЕЛЬСТВА}
% ============================================================

Согласно техническому заданию (раздел 1.4), система должна соответствовать
Федеральному закону № 152-ФЗ «О персональных данных» и Федеральному закону
№ 149-ФЗ «Об информации, информационных технологиях и о защите
информации». Ниже -- не повтор требований, а то, что из них фактически
реализовано в коде к моменту завершения практики.

\begin{itemize}
  \item \textbf{Согласие на обработку персональных данных.} Форма
        регистрации требует явной отметки согласия (чекбокс со ссылкой на
        политику конфиденциальности) -- отправка формы блокируется, пока
        согласие не отмечено; то же условие распространено на вход через
        VK ID (кнопка входа через VK неактивна без отметки согласия).
  \item \textbf{Страница политики конфиденциальности} (маршрут
        \texttt{/privacy}, ссылка -- в подвале сайта и на форме
        регистрации) -- десять разделов, соответствующих типовой структуре
        документа по 152-ФЗ (правовые основания, категории данных, цели
        обработки, права пользователя, раскрытие использования cookie и
        аналитики, контактные данные оператора и т.\,д.).
  \item \textbf{Честно задокументированное ограничение.} Раздел
        реквизитов оператора персональных данных на странице политики
        сам себя помечает как незаполненный шаблон (плашка «сайт в
        разработке», поля наименования/ИНН/ОГРН -- заглушки) и прямо
        указывает, что документ не имеет юридической силы по 152-ФЗ до
        заполнения реальными реквизитами. Это осознанное решение, а не
        недосмотр: механизм (форма согласия, страница политики,
        раскрытие использования аналитики) реализован полностью, реальные
        юридические реквизиты появятся при регистрации барбершопа как
        оператора персональных данных вне рамок учебной практики.
  \item \textbf{Раскрытие использования cookie и аналитики.} Отдельного
        баннера согласия на cookie нет -- используется формулировка
        «продолжение использования сайта означает согласие», раскрытая в
        §8 политики конфиденциальности вместе с фактом использования
        Яндекс.Метрики (раздел 9.2).
  \item \textbf{Хранение и удаление персональных данных.} Пароли не
        хранятся в открытом виде (хэш пароля, поле \texttt{password\_hash});
        удаление учётной записи при наличии связанных записей о визитах
        технически заблокировано ограничением ссылочной целостности
        (\texttt{ON DELETE RESTRICT}) -- вместо удаления применяется мягкая
        блокировка (\texttt{is\_blocked}), что само по себе требование
        к порядку последующей ручной обработки запросов на удаление
        данных вне объёма настоящей практики.
\end{itemize}

\section{ПОДКЛЮЧЕНИЕ АНАЛИТИКИ}
% ============================================================

В системе три независимых источника аналитики, которые не стоит путать
между собой:

\begin{itemize}
  \item \textbf{Веб-аналитика (Яндекс.Метрика) -- подключена и активна.}
        Счётчик загружается отдельным статическим файлом
        (\texttt{/metrika.js}), а не инлайн-скриптом в
        \texttt{index.html}, -- сознательное решение ради политики
        безопасности контента (CSP): \envvar{script-src} остаётся
        \texttt{'self'} без исключения \envvar{'unsafe-inline'}.
        Включены \texttt{webvisor}, \texttt{clickmap}, отслеживание
        переходов и точный подсчёт отказов. Использование раскрыто в §8
        политики конфиденциальности (раздел 5).
  \item \textbf{Мониторинг ошибок (Sentry) -- код готов, отключён по
        умолчанию.} Инициализация присутствует и на бэкенде, и на
        фронтенде, но выполняется только при заданном
        \texttt{SENTRY\_DSN}/\texttt{VITE\_SENTRY\_DSN} -- до появления
        учётной записи Sentry (или self-hosted-аналога) обе интеграции
        неактивны. Порядок подключения -- руководство администратора,
        раздел 3.4.3.
  \item \textbf{Бизнес-аналитика -- собственные отчёты по данным
        приложения.} Отдельно от двух пунктов выше: раздел «Статистика»
        (KPI-плитки, график регистраций за 30 дней) и раздел «Отчёты»
        (выручка и загруженность по дням/мастерам/услугам с экспортом в
        Excel) -- оба на данных из собственной БД проекта, без внешнего
        сервиса. Реализуют цель технического задания «формирование
        отчёта по выручке и загруженности без привлечения разработчика»
        (раздел 2.2); полное описание экранов -- руководство
        пользователя, раздел 3.4.3.
\end{itemize}

\section{РАЗМЕЩЕНИЕ В СЕТИ ИНТЕРНЕТ}
% ============================================================

Полный порядок развёртывания, включая перечень необходимых портов,
подключение домена и TLS, первичную настройку и восстановление после
сбоя, -- предмет отдельного документа (руководство администратора,
разделы 3.1--3.5) и здесь не повторяется. Кратко: система разворачивается
как согласованный набор Docker-контейнеров (база данных, backend,
frontend, реверс-прокси Caddy с автоматическим TLS-сертификатом
Let's Encrypt, ежедневное резервное копирование), наружу из этой
топологии открыты только порты 80/443 контейнера Caddy, обновление
выполняется вручную одной командой (\envvar{scripts/deploy.sh}) без
автоматического деплоя по CI (раздел 6). На момент завершения практики
система готова к развёртыванию на произвольном сервере с Linux и Docker
по этой процедуре; сквозной пример -- от пустого сервера до работающего
сайта с доменом -- руководство администратора, приложение Г.

\section*{ЗАКЛЮЧЕНИЕ}
\addcontentsline{toc}{section}{ЗАКЛЮЧЕНИЕ}
% ============================================================

За время учебной практики (22.06.2026--10.08.2026) разработана и доведена
до готовности к развёртыванию CMS «Сайтама» -- веб-приложение для
автоматизации онлайн-записи и операционной деятельности сети
барбершопов.

\textbf{Соответствие целям технического задания.} Ключевые измеримые цели
(раздел 2.2 технического задания) обеспечены технически: двойное
бронирование исключено ограничением целостности СУБД, а не
организационно (раздел 8); индивидуальный прайс по мастеру, единое
хранилище данных и отчёт по выручке/загруженности без участия
разработчика -- реализованы и доступны в интерфейсе администратора
(раздел 9.3). Часть целей (снижение доли неявок за счёт напоминаний,
доля клиентов, выбирающих вход через VK ID) сформулирована как
показатель, измеримый только на реальной эксплуатации, -- их фактическое
достижение не может быть подтверждено на этапе практики и требует данных
работающей системы после ввода в реальную эксплуатацию.

\textbf{Осознанно суженный или отложенный объём.} Три пункта
первоначального технического задания не реализованы -- и в каждом случае
это задокументированное решение, а не забытая работа: второй OAuth-провайдер
MAX ID (реализован только VK ID, раздел 3); каналы уведомлений
Telegram Bot API и SMS (реализован только email, раздел 2); отдельная
таблица журнала аудита критичных операций \texttt{audit\_log} (частично
закрыта таблицей попыток входа \texttt{login\_attempts}, раздел 7).
Отдельно, очередь фоновых задач Celery + Redis из технического задания
сознательно заменена более простым внутрипроцессным
\texttt{asyncio}-планировщиком (раздел 5) -- здесь не сужение
функциональности, а инженерное решение в пользу меньшей эксплуатационной
сложности при заданном ограничении «один экземпляр backend».

\textbf{Направления дальнейшего развития.} Второй OAuth-провайдер и
дополнительные каналы уведомлений можно добавить без изменения
архитектуры (раздел 3 уже отделяет бизнес-логику сервисов от конкретного
канала доставки/провайдера); горизонтальное масштабирование backend
потребует пересмотра внутрипроцессных механизмов защиты от перебора
паролей и ограничения частоты запросов (раздел 5) в пользу общего
хранилища состояния; полноценный журнал аудита -- отдельная таблица с
записью каждой критичной операции, а не только попыток входа.

Итоговое состояние проекта, полный перечень функциональных требований и
инструкции по эксплуатации -- см. соответственно техническое задание,
руководство пользователя и руководство администратора.
