\textbf{Область применения документа.} Документ описывает установку и
эксплуатацию серверной части CMS «Сайтама»: состав компонентов
развёртывания, требования к серверу, порядок первого запуска, настройку
переменных окружения, обновление версии, резервное копирование и
восстановление данных, мониторинг состояния и типовые нештатные ситуации.
Документ не описывает бизнес-логику и пользовательский интерфейс
системы.

\textbf{Перечень эксплуатационной документации.} Работа с
пользовательским интерфейсом (личный кабинет клиента и мастера, панель
администратора точки и владельца сети) описана в отдельном руководстве
пользователя. Программный интерфейс (API) документирован автоматически
средствами FastAPI в формате OpenAPI/Swagger и доступен по адресу
\texttt{/api/docs} развёрнутого экземпляра системы. Настоящий документ
самодостаточен для задач установки и сопровождения.

\textbf{Уровень подготовки пользователя.} Документ рассчитан на читателя
с базовыми навыками работы в командной строке Linux, начальным опытом
работы с Docker и Docker Compose, общим представлением о переменных
окружения и настройке DNS-записей домена. Для операций резервного
копирования/восстановления и для запуска системы без Docker
дополнительно полезны базовые навыки работы с PostgreSQL
(\texttt{psql}, \texttt{pg\_dump}).

% ============================================================
\gostsection{1}{НАЗНАЧЕНИЕ ПРОГРАММЫ}
% ============================================================

CMS «Сайтама» -- веб-приложение для автоматизации онлайн-записи клиентов и
операционной деятельности сети парикмахерских/барбершопов; назначение и
функции системы с точки зрения пользователей подробно описаны в
руководстве пользователя (раздел 1 того документа). Настоящий раздел
описывает систему со стороны того, что администратор фактически
разворачивает и поддерживает на сервере.

Система разворачивается как набор взаимодействующих контейнеров Docker:
веб-сервер с TLS-терминацией и security-заголовками (Caddy), контейнер
фронтенда (отдаёт собранное веб-приложение и проксирует запросы к API),
контейнер бэкенда (FastAPI/Python) и сервер базы данных (PostgreSQL), а
также контейнер автоматического резервного копирования. Ниже приведена
общая схема состава развёртывания.

\begin{enumerate}
  \item Браузер клиента обращается к \textbf{Caddy} (TLS-терминация,
        порты 80/443, автоматический сертификат Let's Encrypt).
  \item Caddy передаёт запрос контейнеру \texttt{frontend} (nginx:
        отдаёт собранное веб-приложение и проксирует запросы
        \texttt{/api/*} дальше).
  \item Контейнер \texttt{frontend} проксирует \texttt{/api/*} на
        контейнер \texttt{backend} (FastAPI/uvicorn, порт 8000).
  \item Контейнер \texttt{backend} обращается к контейнеру \texttt{db}
        (PostgreSQL 16, порт 5432).
  \item Рядом с \texttt{db} работает контейнер \texttt{backup-local}
        (ежедневный \texttt{pg\_dump} в \texttt{./backups}) и
        опциональный \texttt{backup-s3}.
\end{enumerate}

Наружу из этой топологии открыты только порты 80 и 443 контейнера Caddy --
порты базы данных, бэкенда и фронтенда в продакшен-конфигурации
(\envvar{docker-compose.yml}) на хост не публикуются, обращение к ним
возможно только внутри внутренней docker-сети.

\subsection*{Состав технических и программных средств}
\addcontentsline{toc}{subsection}{Состав технических и программных средств}

\begin{itemize}
  \item \textbf{Сервер (VPS) или иной хост с Linux}, на котором установлены
        Docker Engine и плагин Docker Compose (команда \texttt{docker
        compose}, без дефиса). Конкретные минимальные требования к
        объёму оперативной памяти и числу ядер процессора проектом не
        нормированы -- ориентируйтесь на нагрузочное тестирование перед
        вводом в эксплуатацию; практически достаточно ресурсов для
        одновременной работы шести контейнеров (PostgreSQL, backend,
        frontend, Caddy, ежедневный бэкап и, опционально, S3-бэкап).
  \item \textbf{Открытые наружу порты 80 и 443} (HTTP/HTTPS через Caddy).
        Остальные порты наружу открывать не нужно и небезопасно.
  \item \textbf{Домен с A-записью}, указывающей на IP сервера -- обязателен
        для выпуска TLS-сертификата (Let's Encrypt не выдаёт сертификаты
        по IP-адресу). До появления домена система работает по обычному
        HTTP на голом IP.
  \item \textbf{Настоящий HTTPS-домен обязателен для входа через VK ID} --
        по IP или \texttt{localhost} в проде эта функция не работает.
  \item Для запуска \emph{без} Docker (только для разработки/тестирования,
        не рекомендуется для прод-эксплуатации): Python 3.14, Node.js 18+,
        PostgreSQL 13+ с правами на \texttt{CREATE EXTENSION} (нужно
        расширение \texttt{btree\_gist}).
  \item Для просмотра/восстановления резервных копий -- программы
        \texttt{gunzip} и \texttt{psql} (входят в стандартный образ
        PostgreSQL, используемый в \texttt{docker compose exec}).
\end{itemize}

\subsection*{Условия применения}
\addcontentsline{toc}{subsection}{Условия применения}

Система рассчитана на постоянное подключение сервера к Интернету и на
работу \textbf{ровно одного} экземпляра контейнера \texttt{backend} --
защита от перебора паролей, планировщик напоминаний о записи и
ограничение частоты запросов реализованы внутри процесса бэкенда, без
внешней очереди задач или общего хранилища состояния между экземплярами.
Горизонтальное масштабирование бэкенда (несколько одновременно
работающих реплик) в текущей версии системы не поддерживается.

\gostsubsection{3.1}{Развёртывание через Docker Compose (рекомендуемый способ)}

\begin{enumerate}
  \item Установите Docker, если он ещё не установлен:
\begin{verbatim}
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER && newgrp docker
\end{verbatim}
  \item Скопируйте код на сервер и перейдите в каталог проекта:
\begin{verbatim}
git clone https://github.com/Stonuv/fastapi_hair_salon
cd fastapi_hair_salon
cp .env.example .env
\end{verbatim}
  \item Заполните в файле \texttt{.env} обязательные значения
        \texttt{SECRET\_KEY} и \texttt{SETUP\_TOKEN} -- без них контейнер
        \texttt{backend} откажется запускаться (см. 5). Команды
        генерации приведены прямо в комментариях файла:
\begin{verbatim}
python3 -c "import secrets; print(secrets.token_urlsafe(48))"  # SECRET_KEY
python3 -c "import secrets; print(secrets.token_urlsafe(24))"  # SETUP_TOKEN
\end{verbatim}
        Остальные переменные (\texttt{SITE\_ADDRESS}, \texttt{COOKIE\_SECURE},
        \texttt{SMTP\_*}, \texttt{VK\_*}) можно оставить закомментированными --
        система заработает по IP на голом HTTP. Полный перечень -- приложение А.
  \item Откройте необходимые порты в брандмауэре:
\begin{verbatim}
sudo ufw allow OpenSSH
sudo ufw allow 80,443/tcp
sudo ufw enable
\end{verbatim}
  \item Запустите стек:
\begin{verbatim}
docker compose up --build -d
\end{verbatim}
        Миграции базы данных накатываются автоматически при старте
        контейнера \texttt{backend}, отдельного шага не требуется.
  \item Откройте \texttt{http://<IP сервера>/setup} и введите значение
        \texttt{SETUP\_TOKEN} -- это создаёт первого владельца сети и
        первую точку сети (подробный пошаговый разбор мастера настройки --
        в руководстве пользователя, раздел 3.1). После этого
        \texttt{/setup} самоблокируется -- повторно им воспользоваться
        нельзя.
\end{enumerate}

\gostsubsection{3.2}{Подключение домена и HTTPS}

Когда домен готов (A-запись указывает на IP сервера):
\begin{enumerate}
  \item Впишите в \texttt{.env}:
\begin{verbatim}
SITE_ADDRESS=your-domain.ru
COOKIE_SECURE=true
FRONTEND_BASE_URL=https://your-domain.ru
\end{verbatim}
  \item Перезапустите стек: \texttt{docker compose up -d} -- Caddy сам
        получит сертификат Let's Encrypt и включит редирект
        \texttt{http -> https}, без ручной правки \texttt{Caddyfile}.
\end{enumerate}
После этого можно донастроить вход через VK ID (redirect URI приложения
и \texttt{VK\_REDIRECT\_URI} -- на
\envvar{https://your-domain.ru/api/auth/vk/callback}) и подключить
боевой SMTP-провайдер (см. 3.3).

\gostsubsection{3.3}{Настройка почты (SMTP) и входа через VK ID}

\textbf{Почта.} Без заполненных \texttt{SMTP\_*} переменных попытки
отправки писем (подтверждение почты, восстановление пароля,
напоминания, перенос записи) молча падают в лог контейнера
\texttt{backend} -- само приложение при этом не ломается. Для боевого
провайдера заполните \texttt{SMTP\_HOST}, \texttt{SMTP\_PORT},
\texttt{SMTP\_USER}, \texttt{SMTP\_PASSWORD}, \texttt{SMTP\_USE\_TLS},
\texttt{SMTP\_FROM\_EMAIL}, \texttt{SMTP\_FROM\_NAME} в \texttt{.env}
(пример для Яндекс.Почты -- \texttt{smtp.yandex.ru:465},
\envvar{SMTP\_USE\_TLS=true}, пароль -- «пароль приложения»,
\envvar{id.yandex.ru/security}, а не обычный пароль от почты).

\textbf{Локальная проверка почты (только для разработки).} Поднимите
Mailpit -- фейковый SMTP-сервер, перехватывающий письма вместо реальной
отправки:
\begin{verbatim}
docker compose -f docker-compose.dev.yml up -d
\end{verbatim}
Дефолты в \envvar{backend/.env.example} уже нацелены на него
(\envvar{SMTP\_HOST=localhost}, \envvar{SMTP\_PORT=1025}); письма
смотрите на \envvar{http://localhost:8025}.

\textbf{VK ID.} Требует зарегистрированное приложение на
\envvar{id.vk.com/business}: создайте приложение, укажите redirect URI
\envvar{https://<домен>/api/auth/vk/callback} (в проде -- только
настоящий HTTPS-домен, не IP и не \texttt{localhost}) и впишите
\texttt{client\_id}/\texttt{client\_secret} в \texttt{VK\_CLIENT\_ID}/
\texttt{VK\_CLIENT\_SECRET}. Без \texttt{VK\_CLIENT\_ID} кнопка «Войти
через VK» на сайте автоматически скрывается -- это ожидаемое поведение,
а не ошибка.

\gostsubsection{3.4}{Первичная настройка приложения}

Создание первого владельца сети и первой точки сети выполняется через
мастер \texttt{/setup} сразу после запуска стека (см. шаг 6 в 3.1).
Полный пошаговый разбор этого мастера (все четыре шага, поля формы,
подсказки) приведён в руководстве пользователя, раздел 3.1 -- с точки
зрения администратора здесь важно только то, что до этого момента сайт
недоступен для обычных посетителей, а после -- мастер настройки
самоблокируется навсегда.

\gostsubsection{3.5}{Проверка работоспособности}

\begin{enumerate}
  \item Убедитесь, что все контейнеры запущены и здоровы:
\begin{verbatim}
docker compose ps
\end{verbatim}
        У каждого сервиса со своим healthcheck (\texttt{db},
        \texttt{backend}, \texttt{frontend}, \texttt{caddy}) в колонке
        состояния должно быть \texttt{healthy}. Запуск идёт по цепочке
        зависимостей: \texttt{backend} стартует только после того, как
        \texttt{db} стал healthy; \texttt{frontend} -- после
        \texttt{backend}; \texttt{caddy} -- после \texttt{frontend}.
  \item Проверьте состояние приложения напрямую:
\begin{verbatim}
curl http://<IP или домен>/api/../health   # либо откройте в браузере
\end{verbatim}
        Ожидаемый ответ -- \texttt{\{"status": "ok"\}}. Ответ
        \texttt{503} со сведением \texttt{"database unavailable"}
        означает, что бэкенд поднялся, а база данных -- нет (см. 5).
  \item Откройте сайт в браузере и убедитесь, что главная страница
        загружается, а \texttt{/api/docs} показывает документацию API.
\end{enumerate}

\gostsubsection{4.1}{Обновление развёрнутой версии}

Автоматического развёртывания по push/merge в проекте нет -- обновление
выполняется вручную на сервере одной командой:
\begin{verbatim}
./scripts/deploy.sh
\end{verbatim}

\begin{enumerate}
  \item \texttt{git pull --ff-only}.
  \item \texttt{docker compose up --build -d --wait --wait-timeout 120}.
  \item Ожидание healthcheck всех сервисов.
  \item Успех -- либо ненулевой код завершения при неудаче (сломанный
        деплой не остаётся молча висеть).
\end{enumerate}

Скрипт выполняет \texttt{git pull --ff-only}, пересобирает и
перезапускает стек и дожидается healthcheck-статуса
\texttt{backend}/\texttt{frontend}/\texttt{caddy}, прежде чем считать
обновление успешным; если после пересборки какой-то из сервисов не стал
healthy -- скрипт завершается с ошибкой. Миграции базы данных
накатываются автоматически при старте контейнера \texttt{backend},
отдельного шага не требуется. Отката (rollback) на предыдущую версию
скрипт не выполняет -- это осознанное ограничение (см. также раздел
«Известные ограничения» README.md проекта).

\gostsubsection{4.2}{Резервное копирование и восстановление базы данных}

\textbf{Автоматическое локальное копирование.} Контейнер
\texttt{backup-local} поднимается сразу вместе с остальным стеком, без
дополнительной настройки: ежедневный сжатый \texttt{pg\_dump} в
каталог \texttt{./backups} рядом с \envvar{docker-compose.yml}, с
ротацией -- 7 ежедневных, 4 еженедельных, 6 ежемесячных копий (значения
\envvar{BACKUP\_KEEP\_DAYS}/\envvar{BACKUP\_KEEP\_WEEKS}/
\envvar{BACKUP\_KEEP\_MONTHS} в \envvar{docker-compose.yml}). Каталог
\texttt{./backups} смонтирован с диска сервера (не именованный том
Docker), поэтому копии видны и доступны для передачи на другую машину
(\texttt{rsync}/\texttt{scp}) -- сам по себе локальный бэкап не защищает
от потери всего сервера или его диска целиком.

\textbf{Дополнительное копирование в S3 (опционально).} Второй,
независимый бэкап во внешнее S3-совместимое хранилище (Yandex Object
Storage, Selectel, Backblaze B2, AWS S3 и т.\,п.) переживает потерю
самого сервера:
\begin{enumerate}
  \item заполните \texttt{S3\_BACKUP\_*} переменные в \texttt{.env}
        (endpoint, регион, бакет, ключи доступа);
  \item запустите: \texttt{docker compose --profile s3-backup up -d}.
\end{enumerate}
Без заполненных переменных контейнер \texttt{backup-s3} не
запускается вовсе (профиль \texttt{s3-backup} по умолчанию выключен).

\textbf{Восстановление из резервной копии.}
\begin{enumerate}
  \item Найдите самый свежий дамп:
\begin{verbatim}
ls -t backups/barbershop/daily/*.sql.gz | head -1
\end{verbatim}
  \item Остановите бэкенд (чтобы он не писал в базу во время
        восстановления):
\begin{verbatim}
docker compose stop backend
\end{verbatim}
  \item Восстановите базу из дампа:
\begin{verbatim}
gunzip -c backups/barbershop/daily/barbershop-<дата>.sql.gz | \
  docker compose exec -T db psql -U barbershop -d barbershop
\end{verbatim}
  \item Запустите бэкенд обратно:
\begin{verbatim}
docker compose start backend
\end{verbatim}
\end{enumerate}

\gostsubsection{4.3}{Мониторинг состояния}

\begin{itemize}
  \item \texttt{docker compose ps} -- быстрый обзор состояния всех
        контейнеров (\texttt{running}/\texttt{healthy} или нет).
  \item \texttt{docker compose logs <сервис>} (например,
        \texttt{docker compose logs backend}) -- журнал конкретного
        контейнера; добавьте \texttt{-f} для просмотра в реальном
        времени.
  \item \texttt{GET /health} -- проверка самого приложения и его связи с
        базой данных (используется healthcheck'ом контейнера
        \texttt{backend} и подходит для внешних систем мониторинга):
        \texttt{200} \texttt{\{"status": "ok"\}} в норме,
        \texttt{503} \texttt{\{"detail":} \texttt{"database} \texttt{unavailable"\}}, если
        приложение не может выполнить простой запрос к базе.
  \item \textbf{Мониторинг ошибок (Sentry) подготовлен, но не
        подключён.} Код инициализации есть и на бэкенде, и на
        фронтенде, но без указанного DSN \texttt{sentry\_sdk.init(...)}
        не вызывается -- мониторинг выключен целиком. Когда появится
        доступ к sentry.io (или self-hosted/GlitchTip-инстансу с DSN
        того же формата):
        \begin{enumerate}
          \item создайте проект, скопируйте DSN;
          \item впишите в \texttt{.env}: \envvar{SENTRY\_DSN=...}
                (бэкенд) и \envvar{VITE\_SENTRY\_DSN=...} (фронтенд);
          \item для бэкенда достаточно
                \texttt{docker compose up -d backend} (обычная
                переменная окружения контейнера);
          \item для фронтенда \textbf{обязательна пересборка}, а не
                просто перезапуск -- значение запекается в собранный
                бандл на этапе \texttt{npm run build}:
                \texttt{docker compose up --build -d frontend}.
        \end{enumerate}
\end{itemize}

\gostsubsection{4.4}{Управление переменными окружения}

Переменные окружения задаются в двух разных файлах, которые легко
перепутать:
\begin{itemize}
  \item \texttt{.env} в корне проекта (рядом с
        \envvar{docker-compose.yml}) -- читается Docker Compose,
        используется при развёртывании через Docker (см. 3.1);
  \item \texttt{backend/.env} -- читается бэкендом напрямую при запуске
        \emph{без} Docker (нативный локальный запуск, см. README проекта,
        раздел «Вариант 2: локально»).
\end{itemize}
Полный перечень переменных, их назначение и значения по умолчанию -- в
приложении А.

\gostsubsection{4.5}{Безопасность инфраструктуры}

\begin{itemize}
  \item Оба прикладных контейнера (\texttt{backend}, \texttt{frontend})
        работают от непривилегированного пользователя (не \texttt{root}
        внутри контейнера) -- снижает ущерб при компрометации процесса
        внутри контейнера.
  \item Caddy -- единственная точка входа снаружи (порты 80/443) и сам
        проставляет security-заголовки ответа (HSTS,
        \envvar{X-Content-Type-Options}, \envvar{X-Frame-Options},
        \envvar{Referrer-Policy}, \envvar{Permissions-Policy},
        \envvar{Content-Security-Policy}) -- правка \texttt{Caddyfile}
        для этого не требуется.
  \item \texttt{SECRET\_KEY} используется для подписи сессионных
        токенов (JWT) -- при его смене все ранее выданные токены
        перестают проходить проверку подписи, и все пользователи
        мгновенно разлогиниваются. Меняйте его осознанно (например,
        при подозрении на утечку), а не рутинно.
  \item \texttt{SETUP\_TOKEN} нужен только один раз, при первом запуске
        (см. 3.1); после того как первый владелец сети создан, его
        значение уже ни на что не влияет -- эндпоинт \texttt{/setup}
        самоблокируется независимо от него.
  \item Система рассчитана ровно на один экземпляр контейнера
        \texttt{backend} (см. 2, «Условия применения») -- не
        запускайте несколько его реплик одновременно, это нарушит
        защиту от перебора паролей, ограничение частоты запросов и
        рассылку напоминаний (все три реализованы в памяти процесса,
        без внешнего общего хранилища).
\end{itemize}

\subsection*{Действия при сбоях, подозрении на несанкционированный доступ
  и восстановлении}

\begin{itemize}
  \item \textbf{Сайт полностью недоступен.} Проверьте сначала
        доступность самого сервера (сеть, провайдер VPS), затем --
        \texttt{docker compose ps} на сервере. Если один из сервисов
        не запущен -- изучите его журнал (\texttt{docker compose logs})
        и запустите заново (\texttt{docker compose up -d}).
  \item \textbf{Длительный отказ технических средств (сервер
        недоступен продолжительное время).} Разверните систему заново
        на новом сервере по 3.1 и восстановите базу данных из
        последней резервной копии по 4.2 -- при условии, что копии
        предварительно выгружались за пределы исходного сервера
        (S3-бэкап либо ручная выгрузка \texttt{./backups}).
  \item \textbf{Подозрение на несанкционированный доступ к серверу или
        учётным записям пользователей.} На уровне приложения смените
        \texttt{SECRET\_KEY} (мгновенно аннулирует все выданные сессии
        всех пользователей, см. 4.5) и \texttt{SETUP\_TOKEN}.
        Дополнительно проверьте на уровне самого сервера: список
        SSH-ключей и пользователей ОС, правила брандмауэра, журналы
        доступа -- это выходит за рамки настоящей системы и относится к
        общей защите сервера.
  \item \textbf{Восстановление программ.} Код приложения восстанавливается
        повторным разворачиванием из репозитория
        (\texttt{git clone}/\texttt{git pull} + \texttt{docker compose
        up --build -d}) -- сам код не хранит изменяемого состояния,
        вся эксплуатационная информация (пользователи, записи, услуги,
        настройки сайта, загруженные изображения) находится в базе
        данных и в томе \texttt{uploads}, которые резервному
        копированию (4.2) подлежат отдельно.
\end{itemize}

\section*{\hspace*{\gostindent}ПРИЛОЖЕНИЕ Г. Пример развёртывания на новом сервере}
\addcontentsline{toc}{section}{ПРИЛОЖЕНИЕ Г. Пример развёртывания на новом сервере}

Сквозной пример -- путь от пустого VPS до работающего сайта с доменом.

\begin{enumerate}
  \item Арендован новый VPS с Linux, куплен домен
        \envvar{saitama-example.ru}, A-запись домена указывает на IP
        сервера.
  \item На сервере установлен Docker (3.1, шаг 1), склонирован
        репозиторий, создан \texttt{.env} из примера.
  \item Сгенерированы и вписаны в \texttt{.env} значения
        \texttt{SECRET\_KEY} и \texttt{SETUP\_TOKEN} (3.1, шаг 3).
  \item Открыты порты в брандмауэре (3.1, шаг 4).
  \item Выполнено \texttt{docker compose up --build -d}; через
        \texttt{docker compose ps} подтверждено, что все сервисы --
        \texttt{healthy} (3.5).
  \item На \envvar{http://<IP>/setup} введён код настройки, создан
        первый владелец сети и точка «Сайтама на Тверской» (3.4).
  \item В \texttt{.env} прописаны \envvar{SITE\_ADDRESS=saitama-example.ru},
        \envvar{COOKIE\_SECURE=true}, \envvar{FRONTEND\_BASE\_URL=https://saitama-example.ru};
        выполнено \texttt{docker compose
        up -d} -- Caddy автоматически выпустил сертификат (3.2).
        Сайт теперь открывается по HTTPS.
  \item Заполнены \texttt{SMTP\_*} для боевого почтового провайдера
        (3.3) -- проверено восстановление пароля тестового аккаунта,
        письмо получено.
  \item Через месяц эксплуатации вышло обновление кода -- на сервере
        выполнено \texttt{./scripts/deploy.sh}, скрипт подтвердил
        успешный статус всех сервисов (4.1).
  \item Раз в неделю администратор копирует каталог \texttt{./backups}
        на другую машину (\texttt{rsync}) в дополнение к автоматической
        локальной ротации (4.2).
\end{enumerate}
